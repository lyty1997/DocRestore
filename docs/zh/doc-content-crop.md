# 文档模式正文区自动裁剪（OCR 前版面预处理）

> 状态：设计草案（待用户确认）｜创建：2026-06-06｜范围：仅文档模式（代码模式本期不做）

## 1. 背景与目标

文档模式的输入是**屏摄照片**：相机拍下显示器上的在线文档（语雀 / 飞书 / Confluence 等）。
全画面除中间正文外，还包含：

- 顶部：浏览器标签栏 / 操作系统菜单栏
- 左侧：文档站点的**导航树**（目录）
- 右侧：文档**大纲栏**（outline）
- 边缘：桌面、其他设备等杂物

**痛点**：文档模式**没有行号锚定**（代码模式靠行号 + 列检测兜底，质量尚可；文档模式没有），
左右栏、菜单的文字会被 OCR 出来**污染正文**。因此用户此前的工作流是**人工把正文区裁出来**
再喂 OCR——所有历史测试都建立在"已人工裁剪"的图上。

**目标**：用 OCR 前的图像版面分析**自动裁出正文主区域**，替代人工裁剪；同时**兼容已裁剪的图**
（检测到没有侧栏就原样放行，不破坏既有流程）。

**非目标（本期）**：代码模式正文裁剪（已有行号 + 列检测，需求次之）；像素级精确复刻人工裁剪框。

## 2. 需求来源与金标准

- 金标准样本：`test_images/crop_compare/`，同一批文档的「原始全画面」与「人工裁剪正文」一一对应
  （`AI子系统/` vs `AI子系统-裁剪/`）。原图 3488×2624，人工裁剪后约 1700×1500（≈ 原图 33% 面积）。
- 人工裁剪的语义：**保留中间正文栏**（标题 / 正文 / 表格 / 插图），去掉左右栏与顶部 UI；
  裁剪**不追求像素级精确**（裁剪图仍残留少量面包屑、底部设备一角）。

## 3. 可行性验证结论

动手前用 `slide_rectify` 与自写投影 demo 在真实样本上验证（cv2 4.13，样本见 §2）：

| 方案 | 结论 |
|---|---|
| 复用 PPT 的 `slide_rectify`（找最大亮矩形） | **不适用**：文档整屏皆亮，只会框住含左右栏的整屏；占比 ~0.98 等于恒等，且 `top_extend` 反而给正视图加黑边 |
| 现有 `ocr/column_filter`（OCR 后 grounding 坐标过滤侧栏） | 已存在但配置注释写明「PaddleOCR 精度不足，默认关」——正是用户改用人工裁图的原因 |
| 自写投影法（OCR 前图像检测正文列） | **方向可行**：垂直投影能稳定定位正文列**左边界**（各张 x≈920 一致，左导航被排除）；但「完整正文框」会被图表 / 表格等**密度不均**结构带偏（demo 漏掉行间空白大的概述段、右界偏窄） |

**判断**：OCR 前图像裁剪是正确路线，但「鲁棒地框住整个正文区」是个需要迭代的**版面分析 CV 任务**，
非一两个 demo 可直接交付。据此采用**分阶段**推进，先交付价值最高、最鲁棒的部分。

## 4. 方案设计（分阶段）

核心洞察：**真正的痛点是"左右栏污染"，不是"裁剪不够精确"。** 故按"先排除侧栏、再精修边界"分阶段：

### 阶段 1（MVP，本设计主推）：检测正文列左右边界，排除左右侧栏

- 只检测正文主列的**左 / 右边界**（两条贯穿大部分高度的垂直空白沟壑），横向裁掉左导航 + 右大纲。
- **纵向放宽**：上下边界先取整图高度（或仅粗去顶部深色 UI 横条），交给 OCR 引擎自带 grounding 处理。
- 已验证左界稳定，右界用「居中最宽文本列 + 两侧长空白沟壑」检测，比"完整框"鲁棒得多。
- **兼容已裁剪图**：检测不到明显侧栏沟壑（正文已占满宽度）→ 判定为已裁剪，**原样放行**（恒等，不动）。

### 阶段 2：精修上下边界 + 鲁棒化

- 顶部 UI（菜单/标签栏）精确去除；底部设备 / 桌面去除。
- 应对密度不均（标题 / 段落 / 表格 / 插图混排）、多平台版式（语雀 / 飞书 / Confluence）、深色模式。

### 阶段 3（可选）：透视矫正叠加

- 若未裁剪图存在透视畸变（远距离斜拍），在裁剪后叠加透视矫正（复用 `slide_rectify.rectify`）。
- 当前金标准样本均为正视，本阶段优先级最低。

## 5. 算法方案（阶段 1 MVP）

输入原图 BGR，输出正文列裁剪框 `(x0, x1)`（纵向取整高）；任何异常回退原图。

1. 灰度 → 自适应二值化（白底黑字 → 文字前景）。深色模式：按背景亮度判定，必要时反转。
2. 横向强膨胀（核约 81×3）把每行文字连成实条，强化"列"结构。
3. 在中间高度带 `[0.18H, 0.82H]` 做垂直投影 → 列密度曲线（避开顶部 UI / 底部设备）。
4. 阈值分段得"文本列段"（被空白沟壑分隔）；**正文列 = 最宽且居中的列段**，宽度需 > 阈值
   （排除窄侧栏）。
5. 左右边界 = 正文列段 ± 安全余量（偏保守，宁可含少量留白也别切到正文）。
6. **已裁剪判据**：正文列宽 / 图宽 > `crop_skip_ratio`（如 0.90）且无明显左 / 右侧栏沟壑
   → 判为已裁剪，**原样放行**（恒等）。
7. 裁剪 `img[:, x0:x1]`（MVP 纵向整高，左右去栏）。

> demo 已验证步骤 1–4 能稳定定位正文列左界；右界与"最宽列段"判据是阶段 1 的主要调试点。

## 6. 接入与配置

- **接入点**：`_ocr_producer`（`pipeline.py` ~1575，PPT rectify 同位置），OCR 前对 `img` 裁剪得
  `ocr_input` 喂引擎；`page.image_path` 仍指原图（保证 page marker / 前端源图按原文件名匹配）。
  **仅文档模式启用**（PPT 走 rectify、代码模式本期不接）。
- **新模块**：`processing/content_crop.py`，仿 `slide_rectify` 结构：`detect_content_column()` 同步检测
  + `crop_page()` 异步入口（cv2 阻塞走 `asyncio.to_thread`），**任何失败回退原图路径**。
- **配置**：新增 `enable_content_crop: bool = True`（默认开，用户已定）+ 阈值参数
  （`crop_skip_ratio` 等）+ `content_crop_save_debug`（`.content_crop/` 存 before/after 对照）。
- 默认开 + 失败回退 + 已裁剪跳过 → 对已裁剪历史图**无害**（恒等放行）。

## 8. 验收标准

以 `crop_compare` 人工裁剪为金标准（模板匹配把裁剪图定位回原图得 GT 框）：

- **侧栏排除率**：裁剪结果不再包含左导航 / 右大纲文字（目视 + OCR 抽查）。
- **正文覆盖率**：GT 正文区不被裁掉（宁大勿漏）。
- **已裁剪图跳过率**：对 `*-裁剪/` 目录的图，应 100% 判为已裁剪、恒等放行。
- MVP 通过线：多数样本左右栏被排除、正文不漏、已裁剪图全跳过。

## 9. 风险与兜底

- **误裁正文**（最严重）：判据偏保守、安全余量，宁可含少量侧栏也不切正文；任何异常回退原图。
- **多平台 / 深色 / 全屏无侧栏文档**：MVP 先覆盖语雀类白底三栏版式；其余阶段 2 处理，期间靠
  "已裁剪跳过 + 失败回退"保证不劣化。
- **cv2 依赖**：生产已声明 `opencv-python-headless`，dev 环境需 `pip install`（否则 import 失败）。

## 10. 已定决策（2026-06-06 用户确认）

   上下边界精修留阶段 2。
2. **默认开关**：`enable_content_crop` **默认开**（失败回退 + 已裁剪跳过，对历史已裁剪图恒等无害）。
3. **前端**：**加「裁剪预览 + 拖拽微调」入口**——后端自动给建议框，前端逐张展示并允许手动调整后再
   OCR（半自动，沿用人工裁剪习惯做质量兜底）。详见 §11。

## 11. 前端「裁剪预览 + 微调」交互（S3，待细化）

后端自动检测给出每张的建议裁剪框，前端让用户确认 / 微调，最终用确认后的框裁剪再 OCR。
流程候选（S3 开工前定）：

- **方案 A（流程内插确认）**：上传 → 后端逐张检测建议框 → 前端「裁剪确认」步骤（原图 + 可拖拽框）
  → 确认 → 按框裁剪 → OCR。最贴合人工裁剪，但插入新流程步骤。
- **方案 B（先自动后微调重跑）**：先按自动框裁剪跑 OCR；结果页展示每张框，用户微调后「重裁重跑」
  （复用 resume）。改动小，但要先跑一遍。

MVP 后端（S1–S2 + 自动接入）先落地，前端微调在 S3 选定方案后实现。
