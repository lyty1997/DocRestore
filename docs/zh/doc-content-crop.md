# 文档模式正文区自动裁剪（OCR 前版面预处理）

> 状态：设计草案（待用户确认）｜创建：2026-06-06｜范围：仅文档模式（代码模式本期不做）

## 1. 背景与目标

文档模式的输入是**屏摄照片**：相机拍下显示器上的在线文档（语雀 / 飞书 / Confluence 等）。
全画面除中间正文外，还包含：

- 顶部：浏览器标签栏 / 操作系统菜单栏
- 左侧：文档站点的**导航树**（目录）
- 右侧：文档**大纲栏**（outline）
- 边缘：桌面、其他设备等杂物

**痛点**：文档模式**没有行号锚定**（代码模式靠行号 + 列检测兜底，质量尚可；文档模式没有），
左右栏、菜单的文字会被 OCR 出来**污染正文**。因此用户此前的工作流是**人工把正文区裁出来**
再喂 OCR——所有历史测试都建立在"已人工裁剪"的图上。

**目标**：用 OCR 前的图像版面分析**自动裁出正文主区域**，替代人工裁剪；同时**兼容已裁剪的图**
（检测到没有侧栏就原样放行，不破坏既有流程）。

**非目标（本期）**：代码模式正文裁剪（已有行号 + 列检测，需求次之）；像素级精确复刻人工裁剪框。

## 2. 需求来源与金标准

- 金标准样本：`test_images/crop_compare/`，同一批文档的「原始全画面」与「人工裁剪正文」一一对应
  （`AI子系统/` vs `AI子系统-裁剪/`）。原图 3488×2624，人工裁剪后约 1700×1500（≈ 原图 33% 面积）。
- 人工裁剪的语义：**保留中间正文栏**（标题 / 正文 / 表格 / 插图），去掉左右栏与顶部 UI；
  裁剪**不追求像素级精确**（裁剪图仍残留少量面包屑、底部设备一角）。

## 3. 可行性验证结论

动手前用 `slide_rectify` 与自写投影 demo 在真实样本上验证（cv2 4.13，样本见 §2）：

| 方案 | 结论 |
|---|---|
| 复用 PPT 的 `slide_rectify`（找最大亮矩形） | **不适用**：文档整屏皆亮，只会框住含左右栏的整屏；占比 ~0.98 等于恒等，且 `top_extend` 反而给正视图加黑边 |
| 现有 `ocr/column_filter`（OCR 后 grounding 坐标过滤侧栏） | 已存在但配置注释写明「PaddleOCR 精度不足，默认关」——正是用户改用人工裁图的原因 |
| 自写投影法（OCR 前图像检测正文列） | **方向可行**：垂直投影能稳定定位正文列**左边界**（各张 x≈920 一致，左导航被排除）；但「完整正文框」会被图表 / 表格等**密度不均**结构带偏（demo 漏掉行间空白大的概述段、右界偏窄） |

**判断**：OCR 前图像裁剪是正确路线，但「鲁棒地框住整个正文区」是个需要迭代的**版面分析 CV 任务**，
非一两个 demo 可直接交付。据此采用**分阶段**推进，先交付价值最高、最鲁棒的部分。

## 4. 方案设计（分阶段）

核心洞察：**真正的痛点是"左右栏污染"，不是"裁剪不够精确"。** 故按"先排除侧栏、再精修边界"分阶段：

### 阶段 1（MVP，本设计主推）：检测正文列左右边界，排除左右侧栏

- 只检测正文主列的**左 / 右边界**（两条贯穿大部分高度的垂直空白沟壑），横向裁掉左导航 + 右大纲。
- **纵向放宽**：上下边界先取整图高度（或仅粗去顶部深色 UI 横条），交给 OCR 引擎自带 grounding 处理。
- 已验证左界稳定，右界用「居中最宽文本列 + 两侧长空白沟壑」检测，比"完整框"鲁棒得多。
- **兼容已裁剪图**：检测不到明显侧栏沟壑（正文已占满宽度）→ 判定为已裁剪，**原样放行**（恒等，不动）。

### 阶段 2：精修上下边界 + 鲁棒化

- 顶部 UI（菜单/标签栏）精确去除；底部设备 / 桌面去除。
- 应对密度不均（标题 / 段落 / 表格 / 插图混排）、多平台版式（语雀 / 飞书 / Confluence）、深色模式。

### 阶段 3（可选）：透视矫正叠加

- 若未裁剪图存在透视畸变（远距离斜拍），在裁剪后叠加透视矫正（复用 `slide_rectify.rectify`）。
- 当前金标准样本均为正视，本阶段优先级最低。

## 5. 算法方案（阶段 1 MVP）

输入原图 BGR，输出正文列裁剪框 `(x0, x1)`（纵向取整高）；任何异常回退原图。

1. 灰度 → 自适应二值化（白底黑字 → 文字前景）。深色模式：按背景亮度判定，必要时反转。
2. 横向强膨胀（核约 81×3）把每行文字连成实条，强化"列"结构。
3. 在中间高度带 `[0.18H, 0.82H]` 做垂直投影 → 列密度曲线（避开顶部 UI / 底部设备）。
4. 阈值分段得"文本列段"（被空白沟壑分隔）；**正文列 = 最宽且居中的列段**，宽度需 > 阈值
   （排除窄侧栏）。
5. 左右边界 = 正文列段 ± 安全余量（偏保守，宁可含少量留白也别切到正文）。
6. **已裁剪判据**：正文列宽 / 图宽 > `crop_skip_ratio`（如 0.90）且无明显左 / 右侧栏沟壑
   → 判为已裁剪，**原样放行**（恒等）。
7. 裁剪 `img[:, x0:x1]`（MVP 纵向整高，左右去栏）。

> demo 已验证步骤 1–4 能稳定定位正文列左界；右界与"最宽列段"判据是阶段 1 的主要调试点。

## 6. 接入与配置

- **接入点**：`_ocr_producer`（`pipeline.py` ~1575，PPT rectify 同位置），OCR 前对 `img` 裁剪得
  `ocr_input` 喂引擎；`page.image_path` 仍指原图（保证 page marker / 前端源图按原文件名匹配）。

  + `crop_page()` 异步入口（cv2 阻塞走 `asyncio.to_thread`），**任何失败回退原图路径**。

  （`crop_skip_ratio` 等）+ `content_crop_save_debug`（`.content_crop/` 存 before/after 对照）。
- 默认开 + 失败回退 + 已裁剪跳过 → 对已裁剪历史图**无害**（恒等放行）。

## 8. 验收标准

以 `crop_compare` 人工裁剪为金标准（模板匹配把裁剪图定位回原图得 GT 框）：

- **侧栏排除率**：裁剪结果不再包含左导航 / 右大纲文字（目视 + OCR 抽查）。
- **正文覆盖率**：GT 正文区不被裁掉（宁大勿漏）。
- **已裁剪图跳过率**：对 `*-裁剪/` 目录的图，应 100% 判为已裁剪、恒等放行。
- MVP 通过线：多数样本左右栏被排除、正文不漏、已裁剪图全跳过。

## 9. 风险与兜底

- **误裁正文**（最严重）：判据偏保守、安全余量，宁可含少量侧栏也不切正文；任何异常回退原图。
- **多平台 / 深色 / 全屏无侧栏文档**：MVP 先覆盖语雀类白底三栏版式；其余阶段 2 处理，期间靠
  "已裁剪跳过 + 失败回退"保证不劣化。
- **cv2 依赖**：生产已声明 `opencv-python-headless`，dev 环境需 `pip install`（否则 import 失败）。

## 12. 鲁棒化（2026-06-11 落地）

MVP 跑通后做的系统性鲁棒性实验（合成版式矩阵 + 36 张真实原图）暴露三个样本调校假设，
本节记录改造内容与遗留局限。改造后真实样本 35/36 框与旧版一致，1/36（DSC07964，稀疏
术语页）旧版实际裁到左导航被新守卫修复为放行。

### 12.1 改造内容

1. **核宽相对化（消除分辨率耦合）**：膨胀 / 平滑核从固定像素（`(61,3)×2 次迭代`、blur 25px）
   改为按图宽等比（`_DILATE_W_RATIO=0.0345`、`_BLUR_RATIO=0.007`），在校准样本 w=3488 上
   与旧版**严格等效**（横向单侧 ~60px、纵向单侧 2px → 等效单次核 `(121,5)`，核高 5 不可减：
   少 1px 行条变薄，稀疏处投影掉下阈值列段碎裂，实测右边界收窄 76–216px）。效果：同一版式
   跨分辨率行为一致；1280px 宽图沟壑下限从 160px（12.5%w）降到 ~64px（5%w），且窄于下限
   时从"桥接误裁"变为"安全放行"。
2. **选段换"质量 × 中心距离衰减"**：`mass(seg) × (1 − dist(seg中心, 画面中心)/图宽)` 取最大，
   替代旧版"硬中心先验 + 最宽段 fallback"。修复偏拍（正文不跨画面中心）时选错列 / 碰运气；
   稀疏正文页靠衰减压制密集导航。
3. **歧义拒绝守卫**：选中段不含画面中心、且存在质量 ≥ 0.25× 且更靠中心的竞争段 → 判歧义
   返回 None 放行原图（裁错列丢正文远比不裁危险）。该守卫修复了 DSC07964 旧版真实误裁。

### 12.2 测试

`tests/processing/test_content_crop.py::TestRobustness`（12 例参数化）：单左/单右侧栏、特宽/窄
侧栏、窄沟壑 100px、沟壑分隔线、0.5×/1×/3× 分辨率一致性、深色主题、偏拍+稀疏宽右栏、
稀疏正文+密集导航不锚导航。

### 12.3 遗留局限（实验证据，二次踩坑前先读）

- **沟壑 <5%w 桥接**：固有下限（膨胀必须 > 词间距），窄于下限统一安全放行（侧栏残留，OCR
  文本污染由后续链路兜）。
- **分隔线居中于窄沟壑**：宽沟壑下分隔线已无害（质量选段排除桥接段）；窄沟壑 + 居中线仍可能
  POLLUTE。**勿再尝试"二值图减除细长竖线"**：真实照片正文内部恰靠表格边框等细竖线维持投影
  连续，删线把正文拆成两段（36 张回归 7 张劣化，最差丢半列正文），已证伪。
- **同密度等宽双列歧义**：两根同密度同高文本柱（如双栏对照文档）无法分辨哪根是正文，连人也
  需要语义；守卫会放行或按质量选，接受。
- **近恒等灰区**：无侧栏但留白多（正文占比 ~85%）的图可能裁出含全部正文的近恒等框（无内容
  损失）；真实"已人工裁剪"图正文贴边、占比 >0.9 走 skip 不受影响。

## 13. 手动框改任务级生效（2026-06-12，废弃就地预裁剪）

**事故**：用户在 NAS（CIFS 只读挂载，uid=0/file_mode 0755）目录上手动微调裁剪框后建任务，
框完全没生效——旧版 `_apply_requested_crop` → `apply_crop_boxes` **就地覆盖原图**，
`cv2.imwrite` 对无写权限路径返回 False 且代码不检查返回值 → 框**静默丢失**（任务 8caabe3f，
14 张原图全部仍 3488×2624 全尺寸实锤）。该设计的三重问题：① 只读挂载静默失效；② 可写目录
**不可逆毁坏用户原始照片**；③ stage 软链源被 resolve 守卫静默跳过（"选中文件"方式框从未生效）。

**新机制**：手动框走任务级 `OCRConfig.crop_boxes`（相对根 image_dir → (x0,y0,x1,y1)，与
exclude_images 同 key 空间），随 OCR 配置入 DB、resume 自动沿用：
- routes `_resolve_ocr_config`：请求 crop_boxes（剔除被排除图）合入 ocr 配置，不再写盘；
- pipeline `ImageOverrides`（排除 + 用户框）在根入口解析为绝对路径整体下传——顺带修复
  多目录任务 `_process_leaf` 漏传 exclude 的隐藏 bug（根相对 key 在叶子层失配，部分排除静默失效）；
- `_ocr_producer` 预处理优先级：**用户框（crop_page_manual）> PPT 矫正 > 自动检测**；裁剪图落
  `output_dir/.content_crop/{stem}_crop`（与自动同落点），**绝不写用户目录**；
- 副产能力：手动框的 **y0/y1 上下边生效**（旧就地裁剪虽支持但从未可靠工作；自动检测仍整高）。

`apply_crop_boxes` 已删除（源码处留"勿复活"注释）。E2E 实证：软链 stage 源 + 手动框
(900,300,2400,2000) → `.content_crop/DSC07963_crop.JPG` 精确 1500×1700、OCR 目录
`DSC07963_crop_OCR`、NAS 原图完好。

## 14. 扩展到代码 / PPT 模式（2026-06-25 用户确认）

原 §3 范围「仅文档模式」放开。两模式分别处理（用户拍板）：

### 14.1 代码模式：人工裁剪（手动框），不自动裁剪

- 代码模式**坐标依赖强**（`code_assembly` 按 bbox 在原图坐标系重组行/列）+ 已有列裁剪
  （`code_column_ocr`），自动 content_crop（文档正文列检测，未适配 IDE）误裁风险高 →
  **代码模式不自动裁剪**（`skip_content_crop` 仍含 `code_cfg.enable`）。
- 改为放开**手动框**：前端裁剪面板（`cropBoxes` 手动框，原 gated 在 `mode==='doc'`）扩到代码模式。
  后端 `user_box` 分支本就**模式无关**（在 `skip_content_crop` 之前、无条件判定），零改动即生效。
- **澄清（经核实非 bug）**：曾担心「手动裁剪后代码模式源图锚点 overlay 按原图坐标错位」，逐行核对
  否定——代码模式源图**不画任何像素 bbox 叠加层**（`BlockHighlightOverlay` 仅在 `highlight` prop
  存在时渲染，文档/PPT 专属；`CodeViewer` 调 `SourceImageList` 不传 `highlight`/`processed`）；唯一的
  `code-page-anchor` 是画在**代码正文列**里的隐形页边界 span（`top: lineIndex*rowH`），不叠在图上。
  源图显原图、同步靠 `pageKey`=原图名（手动裁剪后 `page.image_path` 还原原图名，pageKey 不变）→ 页级
  同步不受裁剪影响，**无可见错位**。裁剪只改 OCR 输入。
- **决策**：代码模式源图**保持显原图**（用户拍板），需完整 IDE 截图上下文（侧栏/终端）定位代码出处，
  优于显裁剪图。后端 `/processed-image` 已 mode 无关、手动裁剪 `_crop` 天然可被发现，若日后代码模式
  新增源图 bbox 高亮，前端一行 wiring 即接上，非坐标平移难题。

### 14.2 PPT 模式：自动 content_crop，矫正后串联

- PPT 移出 `skip_content_crop`（`skip = code_cfg.enable or is_pdf_rendered_dir`）。
- 预处理由**互斥 `elif`** 改为**串联**：`if 手动框（独占）else { 矫正(若开) → content_crop(若开) }`。
  矫正产 `.rectified/{stem}_after.jpg`，再 content_crop 产 `.content_crop/{stem}_after_crop.jpg`
  （`crop_page` 用输入 stem=`{stem}_after`）。全程 fail-safe（矫正图无空白边 → content_crop 放行）。
- **坐标系**：链末 OCR 图 = `_after_crop`，bbox/image_size 随之；`.ppt_layout.json` 自洽（导出 letterbox
  用 image_size）。
- **高亮 processed-image**：`_processed_source_variants` 加链末变体，探测序
  `_after_crop`（矫正+裁剪）→ `_after`（仅矫正）→ `_crop`（仅裁剪），命中最深处理图对齐。

### 14.3 验收

- PPT+矫正任务：`.content_crop/{stem}_after_crop.jpg` 落盘，OCR 跑在其上；processed-image 返回它、
  高亮对齐。代码模式：手动框生效（crop_boxes 透传），自动裁剪不触发。
